## Findings

1. **P1 — A successful local save can disappear after v14 Continue.** `packages/ui/src/character-life-session.ts:81` returns the upgraded legacy checkpoint before the one-time blocked-storage warning at line 91. When IndexedDB fails, the fallback store lives only in memory. In an independent run through `createCheckpointDeps`, `readLocalCharacterLife`, and `saveLocalCharacterLife`, Continue succeeded, saving revision 1 succeeded, and reopening against the same persistent v14 file returned revision 0. The original survives, but the UI can tell the player the subsequent progress was saved. Preserve the blocked-storage notification on the v14 path and distinguish a volatile save from a durable one.
2. **P2 — A failed v14 local read can write the migration marker.** `packages/ui/src/character-life-session.ts:80` identifies legacy localStorage by the outer version alone. Starting with empty rows, no marker, and the v14 New Game fixture with only its outer `cityRulesetId` deleted, the read refused the checkpoint and wrote `migration:legacy-local-checkpoint = true` through line 89. The nested society still identifies v14. On subsequent reads, the marker suppresses the legacy lookup, even if the version field is restored. Apply the no-write rule to an identifiable damaged v14 source as well as a successful conversion. The marker write comes from the inherited migration path. R1 already checks both version locations for IndexedDB rows.
3. **P2 — The IndexedDB reader accepts a v14 item layout the v14 writer could not produce.** `packages/persistence/src/session-records.ts:114` requires detached item collections for the current ruleset, but a v14 slot with inline collections and no item rows now bypasses reconstruction. The v14 base reader rejected this representation at the same check. I passed the inline fixture through the new historical row writer and reader and got a playable v15 session. Collections embedded in the city row can therefore supply inventory that lacks its required storage rows. Keep portable JSON conversion separate from validation of the original IndexedDB layout. Generate v14 record fixtures with the v14 detachment rules. The new test at `packages/ui/src/__tests__/v14-load.test.ts:35` currently blesses the inline case.
4. **P2 — A damaged v15 file can delete permanent starter rooms.** `packages/core/src/mansion/invariants.ts:32` validates each supplied room and its maximum count, but never requires the Master Suite and Throne Room. I changed only `rooms` to `[]` in the v15 New Game fixture. The public file decoder returned success. Removing just the unoccupied Throne Room also passes the same checks. Both factories grant the rooms permanently and there is no demolition command. A player can lose the Throne Room’s Reports control and be charged to rebuild it. Verify the two starter IDs and types at the playable checkpoint boundary while allowing their later level upgrades.
5. **P2 — A loaded Concubine can enter the Master Suite during R1.** `packages/core/src/mansion/rules.ts:42` implements the future intimate-role exception. I imported a reader-valid Concubine in Maids’ Quarters and dispatched `MOVE_TO_ROOM` for `room-1`. Both the import and the command succeeded, and her household room became `room-1`. Task R1.3 requires `SUITE_ROLE_ONLY` for every Suite move in R1. The existing rejection test uses an NPC with a null role. Enforce the R1 refusal in the shared move rule so the picker and both command routes agree.
6. **P2 — The catalog uses its input to decide which fields and types are valid.** `packages/core/src/mansion/catalog.ts:70` takes the required root keys from the imported JSON. Line 73 checks a numeric field only if the same JSON calls it a number, and line 75 derives the nested keys the same way. Substituting the string `"8"` for `needsGraceWeeks` at JSON module load allowed initialization and produced the string `"18"` for a week-1 player’s grace boundary. The checked-in value is correct. A malformed edit to the manifest can evade import-time diagnostics and break New Game. Validate fixed scalar fields and nested scalar maps against a schema independent of the candidate.
7. **P2 — A new furniture definition still requires a TypeScript edit.** `packages/core/src/mansion/catalog.ts:101` requires exactly the hard-coded IDs from line 29. An additional piece with a valid price, fit room and existing effect is rejected at startup until its ID is also added in TypeScript. Room enumeration likewise comes from `packages/core/src/mansion/types.ts:3`. Spec §2 explicitly requires adding a type using data and existing effects alone. The current 8/8/16 content pin can be tested separately from the runtime definition registry. The current room union can be derived from the shipped catalog.
8. **P2 — Twelve new partial object assertions violate review criterion 1.** `packages/simulation/src/__tests__/mansion-command.test.ts:19` matches only success and the refusal code, and lines 76 and 80 match subsets of the household. Other new sites are `packages/core/src/mansion/__tests__/catalog.test.ts:10` and 11, `packages/persistence/src/__tests__/upgrade-v14.test.ts:98`, 101 and 103, and `packages/ui/src/__tests__/v14-load.test.ts:20`, 62, 63 and 72. The last also uses `stringContaining`, allowing extra local-alert copy. These are additions in new files. Existing strict tests and the exact rendered alert comparisons are still present. Compare the relevant complete values, or select a specific contract field and compare it exactly.
9. **P3 — The exported society type guard accepts an invalid Mansion value.** `packages/core/src/trial/society.ts:67` requires the key but never checks its value. An independent call returned true for `isSocietyState` with `mansion = null`. The full Character Life reader returned false because it also calls the city validator. Direct consumers such as the weekly society input guard at `packages/simulation/src/society-week.ts:174` rely on the narrower predicate. 10. **P3 — The migration tests leave two planned integration cases uncovered.** `packages/ui/src/__tests__/v14-load.test.ts:35` exercises a detached slot with one inventory item, no NPCs and no prior marker.
